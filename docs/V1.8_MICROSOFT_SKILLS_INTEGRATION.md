# ARTEL MCP V1.8 — Microsoft Skills/MCP Integration

## Objective

V1.8 keeps ARTEL as the orchestrator/governor/evidence engine and consumes Microsoft-maintained Power BI tooling as upstream dependencies instead of reimplementing it.

```text
CODEX / LLM
    |
    v
ARTEL MCP ENGINE
    |
    +-- Microsoft Power BI Modeling MCP
    +-- Microsoft Remote Power BI MCP
    +-- Microsoft Power BI report planning/design/authoring skills
    +-- Microsoft report-authoring + Desktop bridge CLIs
    +-- ARTEL Power Automate Engine
    +-- ARTEL Evidence / Guards / Certification
```

## Source-of-truth priority

1. Runtime Modeling MCP evidence
2. Runtime Remote Power BI MCP evidence
3. Runtime Power Automate evidence
4. Fabric definition/API evidence
5. Deterministic Microsoft CLI validation
6. Local PBIP/TMDL inspection
7. Static review
8. Hypothesis

No PASS should be promoted above the evidence actually obtained.

## Microsoft components

### Power BI Modeling MCP

Preferred Tier-1 model engine for semantic-model inspection, DAX, measures, relationships and RLS operations.

Read-first launch used by ARTEL:

```bash
npx -y @microsoft/powerbi-modeling-mcp@latest --start --readonly
```

V1.8 treats it as an external MCP dependency, not vendored Python code.

### Remote Power BI MCP

Remote endpoint:

```text
https://api.fabric.microsoft.com/v1/mcp/powerbi
```

Used for published semantic-model queries/schema when tenant/user permissions allow it. REST ExecuteQueries remains a fallback path rather than the only runtime strategy.

### Power BI Report Authoring

ARTEL adopts the Microsoft workflow contract:

```text
Plan/Design -> Author -> Validate -> Desktop reload -> Screenshot review -> Evidence
```

Local CLI dependencies:

```bash
npm install -g @microsoft/powerbi-report-authoring-cli@latest @microsoft/powerbi-desktop-bridge-cli@latest
```

PBIR metadata must be discovered through the CLI/catalog before writing unfamiliar visual roles, formatting properties, enum values, selectors or expression encodings. ARTEL's own PBIR geometry inspector remains additive.

### Planning and Design contracts

ARTEL reuses the Microsoft separation of responsibilities:

- planning: requirements, dependency checks, locked spec and build sequencing
- design: page archetype, chart choice, color, typography, accessibility and layout contract
- authoring: concrete PBIR mechanics
- semantic model authoring: model/DAX operations, with Modeling MCP as Tier 1

ARTEL adds its own governance requirements around these contracts:

```text
RECOVER
-> INSPECT
-> DEPENDENCY CHECK
-> DESIGN BRIEF
-> DRY_RUN
-> APPROVAL
-> CHECKPOINT
-> BUILD
-> VALIDATE
-> DESKTOP VERIFY
-> RUNTIME VERIFY
-> EVIDENCE
-> COMMIT
-> OPTIONAL DEPLOY
```

## Power Automate placement

Power Automate remains an independent ARTEL engine. It is not moved into the Power BI skills layer.

```text
ARTEL MCP
  +-- Power BI/Fabric adapters
  +-- Power Automate engine
  |     +-- Flow definition/run inspection
  |     +-- recursive action inventory
  |     +-- LLM Adapter / Parse / G1-G8
  |     +-- HTML / email runtime evidence
  |     +-- guarded patch planning
  +-- Evidence/governance
```

Existing V1.7 Power Automate code stays intact in V1.8 and is routed through `artel_v18_route_work(intent="power_automate")`.

## Write policy

V1.8 is still read-first. External components may be write-capable, but ARTEL does not consider that sufficient authorization.

A future write requires all ARTEL guards:

- global writes enabled
- dry-run produced
- explicit confirm
- checkpoint available
- rollback path defined
- evidence captured

The V1.8 Microsoft Modeling MCP example therefore launches with `--readonly`.

## New MCP tools

- `artel_v18_stack_info`
- `artel_v18_dependency_status`
- `artel_v18_route_work`
- `artel_v18_validate_layout_contract`

These tools do not invoke external binaries; they expose deterministic routing, dependency discovery and contract validation.
